## Real defect found by this derivation and fixed

`private.door_checkin_core` did the duplicate check (`count`) and the order read as two statements. If the order disappears between them (event deleted with cascade, or any concurrent delete), the second statement finds no row, the `record` variable stays unassigned, and the next line raised `record "o" is not assigned yet` instead of returning a result. Not a security hole (nothing is admitted; the UI shows "could not check, retry"), but an unhandled exception from the door. Reproduced by test **M36** (it FAILED on the hardened core before the fix, as recorded in `proof/out/` history of this PR's first run), fixed with an `if not found then return invalid` guard (`core:51-53`), and guarded by mutation **D05**. The packs were regenerated by `build.mjs` (`--check` clean); the core md5 therefore changed and the guards were regenerated from it.

## Per-seat vs per-order: options (no choice made)

Current behaviour (proven by M33): one QR = one order; a qty=4 order admits all four people on one scan; the UI shows "Admits 4 people".
1. **Keep per-order** (today). Simple; the door counts people by eye. A party can split only if they share the phone/QR.
2. **Per-seat counter on the order**: add `checked_in_count int` and let each scan admit one seat until `qty` (partial admission); the same QR is scanned up to `qty` times. Needs a schema change and a rule for `checked_in_at` (first or last admission) which readers use today.
3. **One QR per seat** at fulfilment (`fulfill_ticket_order` creates one order row per seat or a seats table). Cleanest for door and resale, largest change (checkout, wallet, app).
4. **Per-order with explicit party-size confirmation** at the door (staff taps how many entered). No schema change if not persisted; weaker audit.
