# 15A + 15B: owner-authorized door scanner (DRAFT; 15B = iPhone camera decoding, stacked on #141; nothing deployed, nothing linked)

The web page and network path for the 12A "real caller / auth contract" (Atlas I08, Nova: "authenticated owner route selected; no self-link scanner accepted"). It calls `public.event_checkin_scan(p_qr_token)` as the signed-in user and shows only token-free, no-contact results.

Behaviour in one paragraph: no session -> `location.replace('/apply?next=%2Fdoor.html')` before any RPC. Otherwise the owner scans with the camera or types the code. Camera decoding: native `BarcodeDetector` when the browser has it and lists `qr_code` (unchanged); otherwise (iPhone Safari) the vendored jsQR decodes frames (see below). Each submit sends exactly one `POST /rest/v1/rpc/event_checkin_scan` with `Authorization: Bearer <the user's access token>`, `apikey: <publishable key>`, body `{"p_qr_token": "<normalised code>"}` (the bug in #139 was the anon key as bearer). The result is mapped by the 12A adapter to one of: Admitted, Already admitted, Not paid, Not your event, Not a KEEPITIL ticket, No code scanned, Sign in to scan, or "Could not check this ticket" (network/server error: never shown as admitted, retry is safe because the server answers `already_used` for a repeat). While a result is on screen the camera loop sends nothing; "Scan next ticket" resumes. The same code scanned again within 4 s is ignored client-side (convenience only: **the server is the real guard**). The code is never put in the URL, history, storage, console or DOM; a code found in the URL is stripped.

**15B: camera decoding without BarcodeDetector (directive D1).** Only when `BarcodeDetector` is missing, throws on `getSupportedFormats()`, or does not list `qr_code`, Start camera lazily adds a same-origin `<script src="/assets/js/vendor/jsqr/jsQR.js?v=1.4.0">` (never before, never on the native path, no CDN). Frames come from the `<video>` onto ONE reused offscreen canvas (never attached to the page), downscaled to at most 640 px wide, one frame every 110 ms (about 9 per second); no frame is read while a result is on screen or the tab is hidden, and the stream is stopped on `pagehide`, hidden, Stop and sign-out exactly as before. jsQR runs with `inversionAttempts: 'dontInvert'`: tickets are dark-on-light, and `attemptBoth` would run a second full decode on every empty frame (about double CPU and heat for a case no ticket uses); a light-on-dark code simply does not scan and the owner types it. The decoded text then takes the SAME path as before (`localParse` -> normalisation/debounce -> one RPC); a URL or garbage QR is refused locally and never sent. If the library fails to load the stream is stopped and the page says "The QR reader couldn't load..." with manual entry still available (a failed load is not cached; tapping Start again retries). The `<video>` has `playsinline` and `muted` in the markup and again at start; `getUserMedia({audio:false, video:{facingMode:{ideal:'environment'}, width:{ideal:1280}, height:{ideal:720}}})` (`ideal`, not `exact`, so a laptop webcam still opens). `door.html` still has no `<script>` for jsQR and is still linked from nowhere.

Design choices worth knowing:
* The scanner does **not** load `keepitil-shell.js` / `keepitil-ai.js` (no bottom nav, no AI widget over a scanner). Header is minimal with a Dashboard link. Fonts are the system stack (no Google Fonts request from a door device).
* Local pre-check: payloads with inner whitespace/control characters, a `://` or > 128 chars are refused without a request. URL-form payloads are **not** accepted: the ticket QR encodes the raw 32-hex token or `KIL-<token>` only (`kil-ticket-qr.js`, `tickets.html:159`; CALLER-CONTRACT does not mention URLs).
* Client-side token shape (32 hex) is deliberately **not** enforced, so a legacy token format would still reach the server (which answers `invalid`).
* The page reads the session with the site's normal Supabase client (`detectSessionInUrl:false`), which keeps its own session where the other pages keep it. This page adds no storage of its own.

Not wired / gates: see `ENABLE-CHECKLIST.md`. `dashboard.html:326` still renders a "Door scanner" link to `/dashboard` (a self-link). Pointing it at `/door.html` is a separate, later change (dashboard.html is not part of this PR).

Run: `npm test` or `node --test assets/js/door-scanner.test.mjs` (needs `jsdom`, already a devDependency).

Not verified: a real iPhone camera / real iOS Safari (the decoder is proven on generated images and in desktop Chrome with a canvas-backed fake camera, not on a lens in a dark room), the real RPC/database, the deployed Pages MIME type for the `.mjs` adapter import (still open, see TEST-PLAN; the vendored jsQR is a classic `.js`, so it has no such risk), VoiceOver/TalkBack, real decode speed on an older iPhone.
